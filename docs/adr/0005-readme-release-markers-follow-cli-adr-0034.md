# README Release Markers Follow `cli` ADR-0034

The README documents exports that the published release does not have, and says so nowhere. `npm dist-tags.latest` is `0.1.0` (2026-11-07), whose `dist/th/index.d.mts` exports `calculateThTax` and no `emitThLevy`; the `## Thailand Levy for sim-core` section on `main` documents `emitThLevy(profile)`, which arrived in #39 after that release. A reader who installs from the page and pastes that example gets `TS2305`, and the page gives no hint that the example needs a newer version. Nothing in `src/` or `scripts/` read the README, so no check could notice.

`trajectonomics/cli` settled the same problem in ADR-0034: a page that describes something the latest release does not have names the release that will ship it, as one visible line `> **Ships in X.Y.Z.**` at the top of the `## ` section it covers, ending at the next `## ` heading, with a strict `X.Y.Z` and no prerelease tag. Nothing else may promise an unreleased export: a section without a marker describes only what the release the reader is running has. This repository adopts that marker, character for character, and requires it for any `## ` section that names a symbol absent from `npm dist-tags.latest`. The canonical decision and its reasoning live in `trajectonomics/cli`; this ADR only records the adoption, as ADR 0004 does for `@trajectonomics/money`.

Enforcement here is offline, and narrower than the original. `bun run check` runs `check:readme`, which compares the README with the `dist` built from the same commit: every `ts` example is typechecked against the built declarations, executed against the built runtime, and its printed line compared with the `text` fence beside it, and every backticked name shaped like this package's public surface must be exported by an entry point. The check never reads the npm registry. That keeps it deterministic, network-free and true for the commit it runs on, and it cannot fail a pull request merely because no release has happened since (AGENTS rule 3).

The online half of ADR-0034 is deliberately not built here yet. It is a workflow job that reads the published `latest`, fails a pull request that promises a symbol that release does not export, and adds a weekly freshness rule so a marker is removed once it has shipped. This repository has cut one stable release, so a weekly run over a handful of markers would report nothing for most of its life, and the freshness rule's cost — a marker can only be cleared after the release it names exists — buys little until releases are frequent. The risk is named rather than hidden: nothing here checks a marker against npm, so a marker that names `0.2.0` stays after `0.2.0` ships, and a marker removed early is not caught either, until a pull request or a later pass reads it. The drift guard proves one direction only — the README and the `dist` of the same commit agree — and that is the accepted gap.

The clearing pull request therefore lands after the release dispatch, in `trajectonomics/infra`, and the marker is the reader-facing record until then. Adopting the online half later is a change to this ADR, not a new decision.
